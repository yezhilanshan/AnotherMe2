# 移动端苏格拉底式教学方法升级计划书

更新时间：2026-06-24

## 1. 总体判断

当前移动端已经完成了“拍题步骤追问”的基础闭环，并在近期补充了 `socratic` 意图、本地追问状态、学习事件回写和知识追踪 evidence。但这仍然不是完整的苏格拉底式教学系统。

问题不在于 prompt 不够像导师，而在于产品机制还没有强制形成：

```text
学生先表达想法 -> 系统诊断想法 -> 选择下一教学动作
             -> 分层提示 -> 变式确认 -> 写回学习画像
```

成熟教学产品的共同点是：不把“问问题”当作苏格拉底教学本身，而是把学生每一次作答当作核心输入，围绕作答质量动态决定下一步引导。

因此，本计划不建议继续堆叠提示词，也不建议直接把 Web 端完整 agentic pipeline 搬到移动端。移动端应建设一个轻量、可控、可验证的“步骤引导工作台”，保留 fast chat 的响应速度，同时补齐作答、诊断、提示、确认和学习画像写回。

## 2. 产品调研结论

| 产品 | 关键机制 | 对 AnotherMe 的启发 |
| --- | --- | --- |
| Khanmigo | 以引导学生自己发现答案为核心，避免直接给答案；结合 Khan Academy 内容库。参考：[Khanmigo](https://www.khanmigo.ai/)、[Khanmigo for teachers](https://www.khanmigo.ai/teachers) | 步骤追问不应默认讲解，而应让学生先观察、猜测和尝试。 |
| ChatGPT Study Mode | 使用苏格拉底问题、提示、自我反思、知识检查，并根据学生水平组织学习过程。参考：[OpenAI Study Mode](https://openai.com/index/chatgpt-study-mode/)、[Study Mode FAQ](https://help.openai.com/en/articles/11780217-chatgpt-study-mode-faq) | 需要明确“学习目标、当前水平、检查题”，不能只围绕一步生成问句。 |
| MATHia | 基于细粒度技能进行个性化反馈、上下文提示和进度追踪。参考：[MATHia](https://www.carnegielearning.com/solutions/math/mathia)、[How MATHia uses AI](https://www.carnegielearning.com/blog/mathia-ai) | 要从“步骤标题”升级为真实知识点/技能标签，并记录提示层级。 |
| ASSISTments | 学生做题过程中获得即时反馈、提示和解释，教师知道谁卡住以及为什么。参考：[ASSISTments](https://www.assistments.org/) | 移动端要记录“卡在哪里、用了几次提示、是否自我修正”，而不是只保存聊天记录。 |

## 3. 当前差距

已完成能力：

- 拍题步骤可跳转 AI 导师。
- 首轮可走 `socratic` prompt，不直接完整讲解。
- 本地保存 `phase / hintLevel / hintsGiven / previousAnswers` 等状态。
- 每轮可写入学习事件。
- 进入确认理解阶段时可写入知识追踪 evidence。

核心缺口：

- 学生没有被产品流程要求先提交“自己的想法”。
- AI 没有专门诊断学生回答，只是根据文本启发式推进状态。
- “给提示 / 直接讲 / 再试一次 / 检查这一步”没有成为结构化教学动作。
- 知识点仍可能是临时 `socratic_step`，缺少真实技能映射。
- 结束条件不严格，学生说“懂了”仍可能被当作完成。
- UI 仍是普通聊天页，不是引导式解题工作台。

## 4. 产品目标

建设移动端“苏格拉底步骤引导工作台”：

```text
拍题生成步骤
  -> 选择某一步进入引导工作台
  -> AI 明确这一步的最小目标
  -> 学生提交自己的判断或下一步
  -> 系统诊断作答
  -> AI 选择反问、轻提示、方向提示、结构化拆解或直接解释
  -> 学生再尝试
  -> 小变式题确认理解
  -> 写回学习事件、知识追踪和复习计划
```

成功标准：

- 学生在获得完整解释前，至少完成一次可记录的尝试。
- 每轮 AI 只执行一个教学动作。
- 系统能区分“没尝试、部分正确、概念误区、计算错误、已理解”。
- 只有通过变式确认后，才写入掌握度正向 evidence。
- 移动端首 token 保持在可演示范围内，不回退到完整深度解题链路。

## 5. 目标用户体验

### 5.1 入口

在拍题步骤卡中保留操作菜单，但重排优先级：

1. 引导我想出来
2. 检查我的下一步
3. 给一点提示
4. 直接解释
5. 生成类似题

默认主入口从“追问这一步”改为“引导我想出来”。

### 5.2 工作台布局

顶部：题目与当前步骤摘要。

中部：教学回合区，按卡片展示：

- 当前目标
- AI 的一个引导问题
- 学生提交的想法
- 系统诊断结果
- 下一步提示

底部：结构化输入区：

- 文本输入：“写下你的想法或下一步”
- 快捷按钮：
  - 我先试试
  - 给一点提示
  - 我卡住了
  - 检查这一步
  - 直接解释

### 5.3 一轮交互示例

```text
AI：这一步的目标是找到角 A 和角 B 的关系。你先观察一下，图里哪两个条件可能让它们相等？

学生：因为这两条边相等，所以两个角相等？

系统诊断：部分正确。学生找到了等边关系，但没有说明对应三角形或等腰三角形依据。

AI：方向对了。再想一步：要从“边相等”推出“角相等”，你需要先确定它们在同一个等腰三角形里吗？
```

## 6. 教学动作模型

新增结构化教学动作：

```ts
type SocraticTeachingAction =
  | "ask_observation"
  | "ask_restate"
  | "ask_next_step"
  | "give_light_hint"
  | "give_directional_hint"
  | "give_structured_hint"
  | "reveal_contradiction"
  | "explain_minimally"
  | "ask_variant_check"
  | "confirm_mastery";
```

动作选择规则：

| 学生状态 | 下一动作 | 说明 |
| --- | --- | --- |
| no_attempt | ask_observation | 只问观察题，不给知识点答案 |
| vague_attempt | ask_restate | 要求学生复述目标或条件 |
| partial_correct | give_light_hint | 轻提示，不展开完整推导 |
| misconception | reveal_contradiction | 用反例或矛盾追问 |
| repeated_confusion | give_structured_hint | 拆成可执行小步骤 |
| asks_direct_answer | explain_minimally | 最小解释，随后要求复述 |
| likely_understood | ask_variant_check | 小变式确认 |
| variant_correct | confirm_mastery | 写入正向 evidence |

## 7. 诊断模型

新增轻量诊断器 `evaluateSocraticAttempt`。第一阶段可走 fast LLM + JSON 输出，后续再替换为规则和学科专用校验器。

输入：

```ts
interface EvaluateSocraticAttemptInput {
  problemSummary: string;
  stepTitle: string;
  stepNarration: string;
  stepGoal: string;
  targetKnowledgePointIds: string[];
  currentPhase: SocraticPhase;
  hintLevel: number;
  promptQuestion: string;
  studentAttempt: string;
}
```

输出：

```ts
interface SocraticAttemptEvaluation {
  verdict: "no_attempt" | "incorrect" | "partial" | "correct" | "misconception";
  confidence: number;
  misconceptionType?:
    | "concept_gap"
    | "condition_misread"
    | "formula_misuse"
    | "calculation_error"
    | "logic_jump"
    | "representation_gap";
  conciseDiagnosis: string;
  nextAction: SocraticTeachingAction;
  shouldIncreaseHintLevel: boolean;
  shouldAskVariant: boolean;
  extractedKnowledgePointIds: string[];
}
```

约束：

- 诊断器不直接面向学生展示原始 JSON。
- 低置信度时不能写知识追踪，只能写学习事件。
- 只有 `verdict=correct` 且通过变式题，才更新 mastery。

## 8. 数据模型调整

### 8.1 扩展移动端状态

在 `SocraticFollowupState` 基础上补充：

```ts
interface SocraticFollowupState {
  stepGoal?: string;
  targetKnowledgePointIds: string[];
  teachingActions: SocraticTeachingActionRecord[];
  evaluations: SocraticAttemptEvaluation[];
  variantQuestion?: string;
  variantAnswer?: string;
  variantEvaluation?: SocraticAttemptEvaluation;
}
```

### 8.2 学习事件

新增或规范事件类型：

- `socratic_step_started`
- `socratic_attempt_submitted`
- `socratic_attempt_evaluated`
- `socratic_hint_given`
- `socratic_misconception_detected`
- `socratic_variant_assigned`
- `socratic_variant_completed`
- `socratic_step_mastered`

事件 payload 必须包含：

```ts
{
  followup_id: string;
  job_id?: string;
  step_id?: number;
  step_title: string;
  step_goal?: string;
  knowledge_point_ids: string[];
  phase: string;
  hint_level: number;
  action: string;
  verdict?: string;
  misconception_type?: string;
}
```

### 8.3 知识追踪

知识追踪写入规则：

- `variant_correct` -> `processQuizAnswer(..., is_correct: true)`
- `variant_incorrect` -> `processQuizAnswer(..., is_correct: false)`
- 普通提示和困惑只写 learning event，不写 quiz evidence
- 无真实知识点时只保留 learning event，不创建临时 mastery

## 9. 后端与 API 计划

### 阶段一：移动端本地优先

不新增后端接口，复用：

- `/v1/ai/chat`
- `/v1/users/{user_id}/learning-events`
- `/v1/users/{user_id}/quiz-answers`

移动端新增本地模块：

- `mobile/lib/socratic-workbench.ts`
- `mobile/lib/socratic-evaluator.ts`
- `mobile/lib/socratic-actions.ts`

### 阶段二：Gateway 轻量诊断接口

新增：

```text
POST /v1/socratic/evaluate-attempt
POST /v1/socratic/next-action
```

这样可以把诊断逻辑从客户端抽出，并统一 Web 与移动端。

### 阶段三：共享包

将类型与状态机迁移到：

```text
AnotherMe/packages/teaching-core/
```

包含：

- `SocraticChainState`
- `SocraticTeachingAction`
- `SocraticAttemptEvaluation`
- `advanceSocraticState`
- `selectNextTeachingAction`

移动端和 Web 端都只依赖该包，不互相 import 源码。

## 11. 验收指标

产品指标：

- 首轮 AI 直接给完整答案比例：0%
- 学生首轮尝试率：>= 80%
- 每轮 AI 多问题输出比例：<= 10%
- 变式确认完成率：>= 50%
- 学习事件完整率：>= 95%

教学质量指标：

- 能识别至少 5 类误区：概念缺口、条件误读、公式误用、计算错误、逻辑跳步。
- 同一学生连续困惑时，提示层级会递进。
- 学生答对时，不继续重复讲解，而是进入变式确认。
- 学生要求直接答案时，系统可以最小解释，但随后要求复述或检查。

工程指标：

- 移动端 `pnpm typecheck` 通过。
- capability 归一化测试通过。
- 工作台无网络时能保留本地状态。
- Gateway 失败时保留普通 fast chat 降级。

## 12. 风险与取舍

### 风险一：诊断不准

LLM 判断学生回答可能误判。第一阶段应把诊断结果作为教学动作参考，不直接作为高权重 mastery evidence。

### 风险二：流程变重

如果每一步都要求学生输入，可能降低爽感。解决方案是保留“直接解释”出口，但把它作为次级路径，并记录为 `direct_explanation_requested`。

### 风险三：知识点映射不稳定

没有真实知识点时不能硬写 BKT。必须允许只写 learning event，等有 `knowledge_point_ids` 后再写 quiz evidence。

### 风险四：移动端性能

不走完整 agentic pipeline。诊断和下一动作生成应尽量合并为一次 fast LLM 调用，输出短 JSON。

## 13. 推荐立即执行项

下一轮建议先做 P0 + P1 的最小闭环：

1. 新建 SocraticWorkbenchScreen。
2. 从拍题步骤跳转到工作台，而不是直接进入普通聊天页。
3. 首屏展示“步骤目标 + 一个引导问题”。
4. 学生必须提交一次想法后，才进入提示或解释。
5. 实现 `evaluateSocraticAttempt` 的 JSON 诊断。
6. 根据诊断选择下一教学动作。
7. 写入 `socratic_attempt_submitted` 和 `socratic_attempt_evaluated`。

暂不做：

- 完整 Web agentic pipeline 迁移。
- 复杂教师端报告。
- 多人讨论式苏格拉底课堂。
- 长篇讲义生成。

## 14. 一句话定位

移动端苏格拉底式教学的目标不是“AI 说话更像导师”，而是：

> 让学生先思考，系统诊断思考，再用最小必要提示推动学生自己走到下一步。
