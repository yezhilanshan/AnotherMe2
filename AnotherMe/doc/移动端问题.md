我浏览了当前项目。结论是：Web 端已经是完整主应用，移动端是“可用的 Expo companion 原型”，已经接入部分 Gateway 能力，但还不是 Web 功能等价的移动 App。

**建议执行计划**
1. **P0：先把移动端从原型变成可多人使用的基础 App**
   - 移除硬编码 IP，改成 `EXPO_PUBLIC_GATEWAY_URL`、dev 自动检测、profile 内可临时覆盖。
   - 接入真实认证，至少先做 Gateway token provider 抽象，再接 Supabase/Auth 方案；替换 `BEARER_TOKEN=''` 和 `USER_ID='mobile-user'`。
   - 把会话、消息、反馈从本地状态接到 `api.aiLearning`，补齐 `loadMessages` 和 `submitFeedback` 服务端同步。
   - 先验收：登录后能恢复个人会话，换设备不会串数据。

2. **P0：冻结 Gateway/API Client 合同**
   - 以 Gateway OpenAPI 为准刷新 `@anotherme/api-client` 类型，保留 SSE/上传等手写封装。
   - 对照 Web 的 53 个 Next API route 和 Gateway 当前路由，列出移动端必需 API 缺口。
   - 优先补：用户资料、课堂创建/详情、AI session messages、feedback、push token、离线同步。
   - 先验收：`mobile` 只通过共享 client 调业务接口，禁止页面里继续散落裸 `fetch`，上传/流式除外。

3. **P1：补齐移动端核心用户闭环**
   - 首页：展示真实最近学习、最近课堂、未完成诊断，而不是只显示本地 sessions。
   - AI 对话：历史消息分页、停止/重试、反馈提交、能力结果可视化稳定渲染。
   - 课堂：移动端至少支持查看课堂详情、播放/阅读场景、继续学习；创建课堂可作为第二阶段。
   - 拍题：上传逻辑改为共享上传封装，job 轮询加后台恢复、失败重试、结果落历史。
   - 知识追踪：把诊断结果、薄弱点、教学建议串到 AI 对话上下文。

4. **P1：移动端专属能力**
   - 离线队列改成 AsyncStorage/MMKV 持久化，并只缓存可重放动作。
   - Expo notifications 真接入 dev build/EAS，Expo Go 下保留 stub。
   - 增加深链：通知或 Web 分享能打开指定课堂、活书页、对话。
   - 图片/视频缓存、弱网提示、后台恢复 job 状态。

5. **P2：Web 与移动端产品边界**
   - 不建议直接追求 100% Web 等价。Web 继续承担复杂创作：课堂生成、协作写作、设置中心、PPT/白板编辑。
   - 移动端优先做学习消费和轻创作：AI 对话、拍题、课堂学习、诊断、知识追踪、通知提醒。
   - WebView 只作为过渡，不作为核心体验；现在已有 WebView 组件，但长期要替换成原生页面。

6. **验证计划**
   - Web：在 `D:\AnotherMe-main\AnotherMe` 跑 `pnpm exec tsc --noEmit --pretty false`、相关 `vitest`、必要时 Playwright mobile smoke。
   - 移动端：在 `D:\AnotherMe-main\mobile` 跑 `npm run typecheck`、`npm run test:capability`，补 Jest/RN Testing Library 后跑核心 store/hooks 测试。
   - Python Gateway：按你的说明用 `anotherme` conda 环境跑相关 Gateway 测试；不要用旧的 `AnotherMe-V2` 脚本名作为准绳。

下一步我建议先做 P0 的“认证 + 会话消息服务端同步 + 配置环境化”，这是移动端继续完善前最关键的地基。否则继续堆页面会把固定用户、本地状态、裸 fetch 这些技术债扩散到更多功能里。
