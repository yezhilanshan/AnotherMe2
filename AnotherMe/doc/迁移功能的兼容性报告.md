### 一、活书引擎 (Live Book)

#### CRITICAL — WebSocket 流式推送完全不可用

`live_book.py:650-662` 调用了 `StreamBus` 上不存在的方法：

```python
sub_id = bus.subscribe(BOOK_SOURCE, _forward)   # subscribe() 不接受参数
await bus.wait()                                  # 不存在 wait() 方法
bus.unsubscribe(sub_id)                           # 不存在 unsubscribe() 方法
```

实际 `StreamBus.subscribe()` 签名是 `async def subscribe(self) -> AsyncIterator[StreamEvent]`（零参数，返回异步迭代器）。DeepTutor 的正确用法是：

```python
async for event in bus.subscribe():
    if event.source != BOOK_SOURCE: continue
    await send(_serialize_event(event))
```

**影响**：任何客户端连接 `/live-book/ws` 都会触发 `AttributeError`，WebSocket 实时流完全瘫痪。

#### HIGH — 重复的 WebSocket 路由

| 路由 | 文件 | 协议 |
|------|------|------|
| `/live-book/ws` | `live_book.py:631` | StreamBus 实时推送（**当前已坏**） |
| `/api/live-book/ws` | `messages.py:267` | DB 轮询模式 |

两个端点行为完全不同，前端连接的是前者（`lib/live-book/api.ts:214`）。

#### MEDIUM — DTO 层数据丢失

- `live_book_dto.py:96` — `chapter_to_dto()` 中 `goal` 字段硬编码为空字符串，丢失实际数据
- `live_book_dto.py:20` — `ContentType` 和 `PageStatus` 被导入但未使用（死导入）

#### LOW — QuizAttemptRequest 缺少字段

`live_book.py:105-111` 的 `QuizAttemptRequest` 缺少 DeepTutor 中的 `request_remediation: bool = False` 字段，如果引擎使用此参数则调用会失败。

#### 活书引擎总结

| 严重度 | 问题 | 状态 |
|--------|------|------|
| CRITICAL | StreamBus API 调用方式错误，WebSocket 完全不可用 | 需修复 |
| HIGH | 两个 WebSocket 端点行为不一致 | 需决策 |
| MEDIUM | DTO `goal` 字段硬编码空字符串 | 需修复 |
| LOW | `QuizAttemptRequest` 缺少 `request_remediation` | 需确认 |

`capability-registry.ts:199` 注册了 `co_writer` 能力，但 `orchestration/handlers/` 目录下无对应 handler 文件，co_writer 无法通过 AI-tutor 调度层被触发。

### 三、AI Tutor 前端

#### 导入链完整性：全部通过 ✅

#### HIGH — `code_delta` 事件在 capabilities-route 路径下被前端丢弃

`capabilities-route.ts:348-353` 直接透传 `code_delta` 事件，但前端 `process-sse-stream.ts` 的 `switch` 语句中**没有 `case 'code_delta'` 分支**。

对比 `chat-route.ts:679-688` 正确地将 `code_delta` 转换为 `text_delta`。

**影响**：通过 `/api/capabilities/[capabilityId]` 路径（math_animator、visualize）的代码生成过程中，用户看不到实时代码流。

#### MEDIUM — `thinking` 事件字段不匹配

`deep-solve-handler.ts:145-152` 产出：
```typescript
{ type: 'thinking', data: { content: chunk, stage: 'planning' } }
```

`StatelessEvent` 类型定义期望：
```typescript
{ type: 'thinking', data: { stage: 'director' | 'agent_loading'; reasoning?: string } }
```

字段名 `content` vs `reasoning`，`stage` 值 `planning` 不在联合类型中。前端 `buffer.pushThinking(event.data)` 收到的结构不匹配，thinking 内容可能无法正确显示。

#### MEDIUM — 两套 capability 命名体系依赖手工映射

`chat-route.ts:571-579` 中 `capability` 值（`chat`/`quiz`/`research`）与 `CapabilityId`（`ai_tutor_chat`/`quiz_practice`/`deep_research`）之间通过手工映射表桥接，新增 capability 容易遗漏。

#### LOW — 多处 `as unknown as` 类型绕过

- 所有 handler 通过 `as unknown as CapabilityHandler<never>` 强制注册
- `VisualizeResult` 和 `MathAnimatorResult` 追加了类型中不存在的字段
- `formatCapabilityOutput` 在两个路由文件中完整重复
