## AnotherMe 项目架构分析

### 一、整体架构概览

AnotherMe 是一个**混合架构**项目，包含 **两个后端系统** + **一个前端**：

```
用户浏览器 (Next.js App)
        │
        ├─────────────────────────────────────────────────┐
        │                                                 │
   ┌────▼──────────────────────────────┐    ┌────────────▼───────────┐
   │   TypeScript 后端 (Next.js API Routes) │    │  Python 后端 (FastAPI)   │
   │   app/api/ 目录                   │    │  anotherme2_engine/    │
   │                                  │    │                         │
   │   ┌─ /api/chat ──────────────┐   │    │  ┌─ 智能体系统 ──────────┐│
   │   │  AI SDK + callLLM()      │   │    │  │  perception/planning ││
   │   │  直接调用 LLM            │   │    │  │  execution/foundation ││
   │   ├─ /api/generate/ ────────┤   │    │  ├─ Gateway API ────────┤│
   │   │  场景内容/动作/图像/TTS │   │    │  │  任务队列/文件存储    ││
   │   ├─ /api/live-book/ ──────┤   │    │  ├─ 知识追踪 (BKT) ────┤│
   │   │  交互式书籍             │   │    │  │  贝叶斯知识追踪模型   ││
   │   ├─ /api/auth/ ───────────┤   │    │  └────────────────────────┘│
   │   │  用户认证/登录          │   │    └────────────────────────────┘
   │   ├─ /api/memory/ ─────────┤   │
   │   ├─ /api/notebooks/ 等    │   │
   │   └────────────────────────┘   │
   └───────────────────────────────┘
```

---

### 二、各层职责详解

#### 1. 前端 UI 层 (`app/` 页面目录)
- Next.js 16 + React 19 + Tailwind CSS + shadcn/ui
- 功能页面：AI 导师、课堂、交互式课堂、活书、笔记本、设置、拍题生成视频等

#### 2. TypeScript 后端（Next.js API Routes, `app/api/`）
**这是实际承载大部分业务逻辑的后端**，包含：

| API 路由 | 功能 |
|----------|------|
| `chat` | AI 聊天 + 流式 SSE 响应 |
| `generate/scene-content` | 课堂场景内容生成（调用 LLM） |
| `generate/scene-actions` | 场景动作/动画生成 |
| `generate/image` | AI 图片生成 |
| `generate/video` | AI 视频生成 |
| `generate/tts` | 文字转语音 |
| `live-book/*` | 交互式书籍全套 CRUD + 编译 |
| `auth/*` | 用户注册/登录/登出 |
| `classroom` | 课堂管理 |
| `memory` | 用户记忆服务 |
| `notebooks` | 笔记本 CRUD |
| `web-search` | 网络搜索 |

**关键观察**：这些 API 路由中大量直接调用 LLM（通过 `@/lib/ai/llm.ts` → Vercel AI SDK），没用 Python 后端做中转。

#### 3. Python 后端 (`anotherme2_engine/`)

Python 后端是一个 **FastAPI 应用** + **Agent 系统**，主要负责：

| 模块 | 职责 |
|------|------|
| `api_gateway/` | FastAPI 应用，任务队列（Redis）、文件存储、Capability 注册 |
| `agents/perception/` | 视觉感知：OCR、坐标场景识别、几何图形分析 |
| `agents/planning/` | 教学规划：动画规划、知识追踪、模板检索 |
| `agents/execution/` | 执行：动画生成、语音合成、视频合并 |
| `agents/orchestration/` | 工作流编排 |
| `agents/foundation/` | 基础 Agent 框架、状态管理、学习事件 |

**关键观察**：Python 引擎的实际用途高度集中在 **"拍题生成视频"** 这一条管线上，其他 AI 功能（聊天、出题、书籍生成等）都在 TypeScript 后端完成。

---

### 三、前后端分离分析

**结论：前后端分离确实不够清晰，问题主要体现在以下 4 点：**

#### 问题 1：存在两个后端，职责边界模糊

```
用户请求                          TypeScript 后端       Python 后端
"帮我解这道题"  ──────────────→  app/api/chat
                                  ↓
                             callLLM(OpenAI)
                                  ↓
                             返回流式响应
                                  ↑
                             (完全绕过 Python)

"根据图片生成讲解视频"  ──────→  app/api/problem-video
                                  ↓
                             → anotherme2-gateway.ts
                                  ↓  (HTTP 调用)
                             Python FastAPI Gateway
                                  ↓
                             Agent Workflow 执行
                                  ↓
                             返回视频路径
```

有些 AI 功能（聊天、内容生成）走 **TypeScript 直接调 LLM**，有些（视频生成）走 **TypeScript → Python 管道**。没有一个统一的路由层来决定"什么逻辑该去哪里"。

#### 问题 2：LLM 调用双层分散

```
DeepTutor（对比）:                     AnotherMe（现状）:
┌──────────────┐                      ┌──────────────┐
│ Capability   │                      │ Next.js API  │
│ Orchestrator │                      │ Routes       │
│    ↓         │                      │    ↓         │
│ Python LLM   │                      │ Vercel AI SDK│
│ Factory      │                      │ (callLLM())  │
│    ↓         │                      │    ↓         │
│ Provider A/B │                      │ OpenAI/其他   │
└──────────────┘                      └──────────────┘

                                      ┌──────────────┐
                                      │ Python Agent │
                                      │ System       │
                                      │    ↓         │
                                      │ LangChain    │
                                      │ (独立调 LLM) │
                                      └──────────────┘
```

两个后端各自维护一套 LLM 调用方式：
- TypeScript：`@/lib/ai/llm.ts` 封装 Vercel AI SDK
- Python：`agents/foundation/config.py` 各自配置 API Key

没有统一的 LLM 路由、重试、fallback 机制。

#### 问题 3：Capability 系统重复

Python 端有：[anotherme2_engine/agents/foundation/capability_registry.py](file:///d:/AnotherMe-main/AnotherMe/anotherme2_engine/agents/foundation/capability_registry.py)

TypeScript 端也有：[lib/orchestration/capability-registry.ts](file:///d:/AnotherMe-main/AnotherMe/lib/orchestration/capability-registry.ts)

两者都定义了"能力注册"机制，但互相独立，没有同步。这导致：
- 一个能力要在两个地方注册
- 能力状态可能不一致
- 维护成本翻倍

#### 问题 4：Python 后端能力未充分释放

Python 端有非常完整的 Agent 架构（perception → planning → execution），但目前只服务于**拍题生成视频**这一个场景。对比 DeepTutor：
- DeepTutor 的 Python 后端承担了**所有** AI 业务逻辑
- AnotherMe 的大部分 AI 业务逻辑跑在 TypeScript 里

这意味着：
- TypeScript 后端越来越重（`lib/orchestration/` 里已经有完整的 Capability Runtime + Director Graph）
- Python 后端的 Agent 框架没有被充分利用
- 想复用 Python 的 Agent 能力写新功能，需要在两个后端之间做集成

---

### 四、架构改进建议

| 方向 | 具体做法 | 收益 |
|------|---------|------|
| **统一后端** | 将 TypeScript API Routes 中的 AI 密集型调用（chat、scene-content 等）下沉到 Python FastAPI | 单一后端、统一 LLM 路由/重试/fallback |
| **API Gateway 模式** | 保留 Next.js API Routes 作为轻量 BFF（Backend For Frontend），所有 AI 逻辑走 Python | 明确分层、职责清晰 |
| **统一 Capability 注册** | 选择一端（推荐 Python）作为 Capability 注册中心，TypeScript 通过 API 查询 | 消除重复、状态一致 |
| **Python Agent 框架复用** | 将 DeepTutor 的 BaseAgent + LLM Factory 模式引入 Python 端 | LLM 调用统一、Provider 路由可配 |

简单说：**现在的架构像是有两个"大脑"在各自干活**。DeepTutor 用的是"一个大脑（Python）指挥所有"的模式，而 AnotherMe 是"TypeScript 大脑负责聊天/生成，Python 大脑负责视频"的分布式模式，两者之间缺乏清晰的协作契约。
